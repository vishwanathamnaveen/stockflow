Changing existing code with AI, safely and measurably

The Brownfield Starter Kit lets Claude Code work on an existing codebase without guessing. A requirement or bug never goes straight to code. The kit first builds an evidence-based map of what the change touches. That map decides how much human approval the change needs, and every change ends with a measured result.

See the journey See the architecture
For: sponsors, product owners, engineers, tech leads, service owners, QA and security. Source of truth: the kit's guides docs/01-SETUP.md, 02-CHANGE-FLOW.md, 03-EVALUATION.md and rule 40.

The idea in three sentences

1 · Evidence first

For every request the kit builds a Context Manifest: the code, services, APIs, events, tests, business rules, documents and history the change touches, with computed confidence and risk.

2 · Risk decides the gate

The manifest selects a workflow: low-risk changes go fast, while contract, data, security and multi-service changes need plan approval and owner sign-off. Nobody picks a cheaper path by hand.

3 · Every change is measured

Did the manifest predict the files that really changed? Were the tests run? Each change gets a scorecard, and the pilot ends with a GO / EXTEND / STOP decision based on the numbers.

Why we use it

AI coding assistants are fast on new code. On a large existing system the expensive mistakes come from what they don't see: a consumer in another service, an event subscriber, a business rule, a missing test. The kit turns that blind spot into something you can check.

Code first, not infrastructure first

Many code-intelligence starter kits begin with infrastructure: hosted services that must be set up, connected and kept running before the first question about the code can be answered. This kit starts from the code instead and needs no infrastructure of its own. Every graph and index is built by a Python script in tools/context/ and saved as a file in the repository, so a developer can open it, read the script that made it, and rebuild it.

Infrastructure-first kitsThis kit (code first)
What you runHosted services to provision, secure, back up and upgrade Python scripts on CPU. Graphs are JSON, the manifest is YAML, the search index is a local FAISS file
Inspecting the dataThrough each service's own query tools or console Open graph.json or docs.jsonl in an editor; diff them like any other file
Explaining a resultRetrieval happens inside the services; scores are often not kept Every query, hit and score is written to the manifest's retrieval section, and every impacted symbol carries a why (for example code graph: A calls B)
ReproducibilityDepends on the state of the services at query time Inputs are content-hashed; a stale graph or index is detected and blocks the next step
Where code goesWherever the services are hosted Nowhere. Nothing leaves the machine after the one-time model download
Learning curve for a developerEach service's query language and configuration A few hundred lines of Python per tool, readable top to bottom
The trade-off. There is no ad-hoc graph query language: the traversals the kit needs are written in Python. The FAISS index is an exact in-memory search, which suits repository-sized corpora (the code notes it is fine below about a million documents), not an organisation-wide search service. See How search works for the whole retrieval flow.
What it is not. It is not an autonomous deployer. The agent never commits or pushes; a human reviews every diff. It is not a substitute for service owners. It tells them exactly what to look at.

Architecture

The kit has two halves. A context engine of deterministic Python tools turns the repository into queryable graphs and computes facts. Claude Code agents add judgement on top and must obey what the engine wrote down. Everything runs locally and lives as files in the repository.

Design principles

Tools produce facts, agents add judgement

Files, symbols, consumers, tests, confidence, risk and workflow are computed by scripts in tools/context/, reproducibly. Agents can only append unknowns, conflicts and notes, raise risk or lower confidence.

Everything is a file

Graphs are JSON, the manifest is YAML, the search index is a local FAISS file. No server, no database, and no code leaves the machine. The embedding model downloads once.

Freshness is checked, not assumed

Every artifact carries content hashes of its inputs, the engine version and a build-config hash. Stale graphs stop /build-context and /implement-change until refreshed.

Freshness, safety and portability

Freshness

Inputs are fingerprinted by content (line endings normalised, so Windows and Linux agree). refresh.py --check reports fresh / stale; --stale rebuilds only what changed. One writer at a time (a lock file), stages in dependency order, atomic index replacement. A graph built by another engine version or config counts as stale.

Scope enforcement

After the last edit the engine re-runs the approved seeds against the changed code (--verify-scope). Growth (a new file, consumer, service or gate) is a scope change that recomputes risk and can void approvals.

Languages

The tools run on Python. Code is read with Python's ast or tree-sitter: Java, Kotlin, Groovy, C#, TypeScript, JavaScript, Go, PHP, Ruby, Rust, Scala, Swift, C/C++. Framework presets find routes, events, clients and tables (Spring, FastAPI, ASP.NET Core, NestJS, Express, gin, and more); in-house frameworks get a preset in config/conventions.yaml.

Runtime footprint

CPU only, about 2 GB for the toolchain, no GPU, no service to host. The toolchain is pinned by a lock file and installed by setup_toolchain.py. Graph JSON can be committed so CI checks freshness with refresh.py --check --committed-only.

Deeper dive: docs/reference/ENGINE.md (engine design) and docs/reference/KNOWLEDGE-BASE.md (documents).

What is searched

graphify on its own stores only an id, label, file, line and community per node. enrich_graph.py then writes the missing facts onto each class and method node in graph.json: signature, docstring, fields, route, events, business rules, covering tests and an embedding_text. The graphify views (graph.html, GRAPH_REPORT.md) do not show these fields; open graph.json to see them.

semantic_index.py build turns each enriched node, and a few other sources, into one search document and saves them in graphs/semantic/docs.jsonl:

TypeSourceLinks to codeCan produce a seed
codeenriched graphify nodes (test code excluded)the node's own symbolyes
ruledocs/business-rules.md rowsthe symbols the rule citesyes
apiOpenAPI operationsthe route methodyes
topiccontracts/events.yaml topicspublisher and handler symbolsyes
docdocs/**/*.md, README sectionsnoneno, knowledge only
servicedescriptions in config/services.yamlnoneno, service routing

The text of a code document is its embedding_text. It is built from the code, so comments count only when they are a docstring or fall inside the first 700 characters of the body:

# embedding_text of one code node
<kind> <qualname> in the <service> service (<file>).
  + first paragraph of the docstring (or the module doc)
  + HTTP endpoint METHOD /path · published / handled events
  + Fields: name (type), ...
  + Business rule BR-xx: <rule text>
Name: <qualname split into words>. Signature: <signature>
Code: <first 700 characters of the source>
Each document is scored on its own text. Search never follows graph edges and never mixes in a neighbour's text. A caller can still match a query because the callee's name appears in the caller's own code excerpt, but that is a text match, not a graph step.

Step 1 · Name matching (keyword search on code symbols)

resolve_seeds() in manifest.py matches the request's words against the real names in the symbol index (parsed with Python ast or tree-sitter). It does not use BM25 and has no scores: a name either matches or it does not.

  • Identifiers in the request (reorderPoint, OrderService) match symbols, fields and event topics.
  • Business rule ids (BR-07) resolve to the symbols the rule cites.
  • Phrases of 2–3 words become camelCase or PascalCase names ("order type" → OrderType, "ship date" → shipDate).
  • API paths (GET /orders/{id}) resolve to the route method.
  • Single words match symbol names, except generic words that would match more than 35% of the service's code. Those are ignored and listed in the manifest.

Step 2 · Hybrid search (BM25 + semantic, fused)

search() in semantic_index.py scores every document for each query (the request plus any expansions the builder agent adds in code or domain terms) in two ways:

Dense (FAISS)

The query is embedded with BAAI/bge-small-en-v1.5 and compared by cosine similarity with every document vector. It finds meaning: "stop overselling" can match a stock reservation method that never uses those words.

Keyword (BM25)

Token overlap, weighted so rare words count more. camelCase and snake_case are split first (reorderPoint → reorder point). It finds exact names and domain terms that an embedding can blur.

The two rankings are merged with Reciprocal Rank Fusion (RRF). There is one fused list, not two separate result sets:

fused(doc) = Σ over queries [ 1 / (60 + dense_rank) + 1 / (60 + bm25_rank) ]
# a document with no keyword overlap gets no BM25 term
  • RRF uses ranks, not raw scores. Cosine (0 to 1) and BM25 (unbounded) cannot be compared directly.
  • The constant 60 flattens the curve: appearing high in both lists beats being first in only one.
  • Each expansion adds two more rankings to the sum, so a document found by several phrasings rises.

For seeds, seed_search() then filters the top 10 fused hits:

  1. Type: only code, rule, api and topic hits are kept.
  2. Quality floor: a hit whose dense score is below min_dense_score (0.55) is dropped, so a keyword match alone cannot carry a weak hit.
  3. Links: each remaining hit's links to code symbols become semantic candidates.

Documents under knowledge/ (PDF, Excel, CSV) are searched the same way by knowledge_base.py (top 8 passages above the same floor). Those passages inform the agents' judgement only. They never add files to scope or change scores.

Step 3 · Choosing the seeds

Name-matching results and search candidates are not merged by score. They are combined by priority, because an exact name in the code is stronger evidence than similarity:

SituationSeeds come fromseeds.source
You passed --seed XYour seeds. Search still runs as a cross-check and is recordedexplicit
Name matching found somethingThe name matches. Search candidates are recorded under seeds.semantic_candidates for the builder agent to comparelexical
Name matching found nothingAt most 4 search candidates from the primary service, each within 0.10 of the best score. Confidence in intent is capped at 0.7 and fast-track is not allowedsemantic

In every case the context-builder-agent reads the code, confirms or corrects the seeds, and re-runs with --seed when they are wrong.

Step 4 · Walking the graph from the seeds

The graph is used only now. The walk follows incoming edges, meaning things that depend on a seed. What a seed itself calls is context, not impact.

SetWhat goes inCode
DirectThe seeds; symbols that read a seed field or identifier; symbols with a graphify calls, uses, references or inherits edge into a seed (1 hop) graphify_neighbors() in manifest.py
TransitiveBreadth-first reverse references from the direct set, up to transitive_depth (default 3). Each symbol records its depth and what it references SymbolIndex.dependents() in common.py
Cross-serviceOther services that call or subscribe to the affected code, from the service graph, plus symbols in other services that use the seed identifiersanalyse() in manifest.py

From the affected symbols the engine derives the API endpoints and event handlers reached, the files in the blast radius, the tests to run, the business rules involved, and finally confidence, risk and the workflow.

Key concepts

The vocabulary you will see in every plan and report.

Context Manifest

A YAML file built by a tool (never by hand) for each request: seeds, files, symbols, APIs, events, consumers, tests, business rules, documents, confidence, risk, workflow. artifacts/changes/<id>/context-manifest.yaml.

Seeds

Where the request lands in the code (e.g. orders:domain.cancel_order). Found by name matching and semantic search, then confirmed by the builder agent reading the code.

Blast radius

The files the change may edit: the manifest's files, the supporting files the plan names (contracts, business rules) and their tests. Anything else needs a scope change.

Confidence

Six components (intent, graph freshness, test evidence, dependency clarity, knowledge grounding, unknowns) and a weighted overall. A heuristic, not a probability. Read the components.

Critical gaps

Intent < 0.5, test evidence < 0.4 or dependency clarity < 0.5. Any gap caps overall confidence at 0.60 and must be addressed or explicitly accepted in the plan.

Risk

An additive score from what is touched: public contracts, dependent services, events with subscribers, business rules, persistence, security code. Bands: low ≤ 2, medium ≤ 6, high ≤ 10, critical above.

Mandatory gates

Floors that no score can buy past: contract change, destructive data change, security-sensitive code, missing owner, invalid contract. See gates.

Unknowns

blocking means no code (clarify). major must be answered or deferred with a named owner in the plan. Agents can add unknowns, never remove them.

Enabled services

The list in brownfield.enabled_services of services the agent may change. Empty after setup; a human adds the pilot service. Everything else is analyze-only.

Scope change (amend)

When the change needs more than the manifest predicted, the agent stops and amends the manifest. Risk and workflow are recomputed; a stricter result voids prior approvals.

Episode & lessons

Each change is recorded in artifacts/memory/episodes.jsonl with its outcome and lessons. Future manifests that touch the same files show those lessons.

Scope recall / precision

Recall: share of really-changed files the manifest predicted (a miss is the costly error). Precision: share of predicted files that changed (low costs review time only).

Ground rules (rule 40, in plain words)

No manifest, no change

The change agent refuses to edit product code without a tool-built manifest and a plan marked Ready, with the approval the workflow needs.

Evidence only gets stricter

Agents may add unknowns, raise risk and lower confidence, never the reverse. Only a human can relax evidence, with a dated decision.

Stay inside the blast radius

Need more files, a migration or another service? Stop and amend the manifest. Never widen silently.

Regression is mandatory

Every required check runs, including test suites of impacted consumer services. Failures get at most 3 repair rounds, then go to a human.

Close the loop

Every change ends with a decision ledger, an episode, refreshed graphs and a clean freshness check.

Untrusted text is data

Ticket and email text is scanned. Personal data stops the change until redacted. Embedded instructions are never followed.

"Not found" ≠ "proven absent"

Consumers outside this repo are "not ruled out" unless a service catalogue is configured. Owners confirm before a breaking change.

No invented business rules

Rules, owners, descriptions and tests come from humans or the code. Missing ones are listed as gaps or questions.

Multi-service = change set

Providers ship backward-compatible changes before consumers; the agent works one service at a time in rollout order.

Semantic search always runs

If the search stack is missing, no manifest is written (exit 5). Never switch it off to "get going".

Step 2 · The gate

Chosen by the workflow (table above), not by the engineer. For plan-approve-execute and guarded, the service owner writes the approval line in change-plan.md.

Step 3 · /implement-change <id>: the build

The agent refuses if…

  • there is no manifest, or the plan isn't Ready
  • the approval is missing
  • the service isn't enabled
  • the graphs are stale

Then, in order

  1. Tests first: failing tests per acceptance criterion
  2. Implement inside the blast radius
  3. Refresh graphs + scope check (grew → amend + maybe re-approve)
  4. All required checks → verification.md
  5. Judge + code review (+ security if guarded), max 3 repairs
  6. Episode with lessons; final freshness check
Then you review the diff. The agent never commits or pushes.

Step 4 · /evaluate-change <id>: the scorecard

Takes seconds. Run it for every change, including those that ended in clarify.

CheckIf it fails
task, manifest, impact analysis, plan, ledger all existFAIL
semantic search ran for the manifestFAIL
fast-track despite a critical gapFAIL
files changed outside the predicted scopeFAIL on fast-track ("fast-track incident"), WARN otherwise
verification.md exists for executed changesFAIL if outcome success, else WARN
episode recorded · audit names the task · repair iterationsWARN

Verdict: any FAIL → FAIL; any WARN → ATTENTION; else PASS. Every finding gets a cause, owner and fix. Numbers are never edited and missing evidence is never back-filled.

After at least 5 recorded changes, /evaluate-pilot compares the aggregate numbers with the exit gates and recommends a decision.

The decision

PASS → GO

A human adds the next services to enabled_services.

ATTENTION → EXTEND

Run more changes; the report names the gate that is short.

FAIL → STOP

Fix the causes (seeds, business rules, tests, contracts, thresholds), then re-evaluate.

Confidence calibration. The report shows outcomes per confidence band (≥ 0.80, 0.60–0.79, < 0.60). If the top band doesn't clearly succeed more often, the thresholds tell you nothing for this repo. Re-tune them as a dated human decision.

Toolchain problems

Install only with python scripts/setup_toolchain.py. It applies a lock of every package version tested together, so transformers, huggingface_hub or numpy can't drift. It installs CPU-only torch and fetches the embedding model once.

SymptomFix
No matching distribution for torch / faiss-cpuuse Python 3.12: delete .venv-context, run py -3.12 scripts/setup_toolchain.py
Import or attribute errors inside transformers / huggingface_hub / numpyrerun setup_toolchain.py (reinstalls from the lock); --check lists the drift
CERTIFICATE_VERIFY_FAILEDcorporate proxy: the script uses the OS certificate store; make sure the company root CA is installed. Never disable verification
huggingface.co unreachableset HTTPS_PROXY or HF_ENDPOINT, or share the model: --export-model bge.zip on a working machine, --model-cache bge.zip on yours
download.pytorch.org blockedset PIP_INDEX_URL to the internal mirror and add --torch-index default
Works in your shell, fails in Claude Codeactivate .venv-context before starting Claude Code; every tool must use that python

Limitations & FAQ

Why does our application's CLAUDE.md contain a "Brownfield change path" section?

Claude Code reads CLAUDE.md at the start of every session. The kit's rules (.mdc) and hooks are in Cursor's format and only load when a command points an agent at them. The section is what tells every session, including a plain chat, that existing code changes only through /build-context → /implement-change. The commands themselves live in .claude/commands/. Keep the section; install.py --apply --upgrade refreshes it.

Why can't I see /build-context when I open the starter kit folder?

The kit folder only offers kit-level commands (/setup-context <app>, /install-kit, /toolchain-doctor). Change commands are installed into the application and appear when you open that folder in Claude Code.

Is the confidence score a probability that the change is correct?

No. It's a weighted heuristic calibrated on a single pilot application. Decide on the components and the critical gaps, and use the pilot's calibration table to re-tune thresholds for your repo.

Can the assistant change a service that isn't enabled?

No. Such changes get analyze-only. Split the task per service, or have the tech lead enable the service.

What if a change turns out bigger than the manifest said?

The scope check after the last edit catches it (exit 4). The agent files a scope change; risk and workflow are recomputed, and a stricter result voids earlier approvals.

Does anything leave our machines?

The embedding model downloads once (or comes from a teammate's export); after that, search runs locally on CPU. Optional community labelling of graphs sends summaries off-machine and needs explicit consent.

Known limitations
  • Impact is name-based, not type-resolved: unrelated symbols sharing a name can appear (the engine favours recall).
  • Routes or topics built at run time (reflection, string concatenation, config-driven routing) are not seen.
  • Per-test coverage only where the format records it (coverage.py contexts, lcov); elsewhere tests are selected statically.
  • Consumers outside the repo are "not ruled out" unless a service catalogue is configured.
  • The toolchain lock is verified on Python 3.12 on Windows.
